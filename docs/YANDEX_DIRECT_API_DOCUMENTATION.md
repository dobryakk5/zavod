# Документация для заявки на полный доступ к Yandex Direct API

## Описание программы

Программа предназначена для автоматизированного управления рекламными кампаниями в Yandex Direct через API. Программа выполняет мониторинг кампаний, анализ эффективности, управление ставками и получение отчетов.

---

## 1. Названия методов, которые использует программа

Программа использует следующие методы Yandex Direct API:

1. **Campaigns.get** - получение списка рекламных кампаний и их параметров
2. **AdGroups.get** - получение групп объявлений для кампаний
3. **Keywords.get** - получение ключевых слов и их параметров
4. **Ads.get** - получение объявлений и их статусов
5. **Bids.get** - получение текущих ставок по ключевым словам
6. **Sitelinks.get** - получение быстрых ссылок
7. **Reports.get** - получение отчетов по эффективности кампаний

---

## 2. Схема и последовательность вызова методов

### Основной сценарий работы программы:

```
1. Инициализация клиента
   └─> Настройка токена доступа и параметров rate limiting

2. Получение списка кампаний
   └─> Campaigns.get
       ├─> Параметры: SelectionCriteria (Ids, States, Types)
       └─> Поля: Id, Name, Type, State, Status, DailyBudget, Currency, Funds, Statistics

3. Для каждой кампании получение групп объявлений
   └─> AdGroups.get
       ├─> Параметры: SelectionCriteria.CampaignIds
       └─> Поля: Id, Name, CampaignId, Status, ServingStatus

4. Для каждой группы получение ключевых слов
   └─> Keywords.get
       ├─> Параметры: SelectionCriteria.AdGroupIds
       └─> Поля: Id, Keyword, AdGroupId, CampaignId, Bid, State, Status, StatisticsSearch

5. Получение объявлений для групп
   └─> Ads.get
       ├─> Параметры: SelectionCriteria.AdGroupIds
       └─> Поля: Id, AdGroupId, CampaignId, Type, Status, State, TextAd

6. Получение ставок по ключевым словам
   └─> Bids.get
       ├─> Параметры: SelectionCriteria.KeywordIds
       └─> Поля: KeywordId, AdGroupId, CampaignId, Bid, ContextBid, SearchPrices

7. Получение отчетов (периодически)
   └─> Reports.get
       ├─> Параметры: ReportType, DateRangeType, Format
       └─> Поля: CampaignName, CampaignId, Impressions, Clicks, Cost, Ctr, Conversions
```

### Детальная последовательность:

**Сценарий 1: Получение полных данных по кампаниям**
```
Campaigns.get (1 запрос)
    ↓
AdGroups.get (1 запрос для всех кампаний)
    ↓
Keywords.get (1 запрос для всех групп)
    ↓
Ads.get (1 запрос для всех групп)
    ↓
Bids.get (1 запрос для всех ключевых слов)
```

**Сценарий 2: Мониторинг эффективности**
```
Reports.get (1 запрос)
    ↓
[Обработка данных отчета]
    ↓
[При необходимости] Campaigns.get для обновления статусов
```

**Сценарий 3: Получение быстрых ссылок**
```
Sitelinks.get (1 запрос по требованию)
```

## 3. Частота вызова каждого метода

### Ограничения, которые соблюдает программа:

- **Максимум 5 запросов в секунду** - программа использует 4 запроса/сек для безопасности
- **Максимум 10,000 запросов в день** - программа ограничивает до 9,000 запросов/день
- **Максимум 100 запросов Reports.get в день** - программа ограничивает до 90 запросов/день

### Частота вызова по методам:

| Метод | Частота вызова | Примечание |
|-------|---------------|------------|
| **Campaigns.get** | 1 раз при инициализации, затем не чаще 1 раза в минуту | Используется для получения списка кампаний и обновления статусов |
| **AdGroups.get** | После получения кампаний, не чаще 2 раз в секунду | Вызывается для каждой кампании или батчем для всех кампаний |
| **Keywords.get** | После получения групп, не чаще 2 раз в секунду | Вызывается батчем для всех групп объявлений |
| **Ads.get** | После получения групп, не чаще 2 раз в секунду | Вызывается батчем для всех групп объявлений |
| **Bids.get** | После получения ключевых слов, не чаще 1 раза в минуту | Используется для мониторинга ставок |
| **Sitelinks.get** | По требованию, не чаще 1 раза в минуту | Используется редко, только при необходимости |
| **Reports.get** | Не чаще 1 раза в час, максимум 90 раз в день | Используется для получения отчетов по эффективности |

### Типичные сценарии использования:

**Сценарий A: Ежедневный мониторинг (утром)**
- Campaigns.get: 1 раз
- AdGroups.get: 1 раз
- Keywords.get: 1 раз
- Ads.get: 1 раз
- Bids.get: 1 раз
- Reports.get: 1 раз (за предыдущий день)
- **Итого: 6 запросов**

**Сценарий B: Получение полных данных (раз в 5 минут)**
- Campaigns.get: 1 раз
- AdGroups.get: 1 раз
- Keywords.get: 1 раз
- Ads.get: 1 раз
- Bids.get: 1 раз
- **Итого: 5 запросов каждые 5 минут = 60 запросов в час = 1,440 запросов в день**

**Сценарий C: Получение отчетов (каждый час)**
- Reports.get: 1 раз
- **Итого: 24 запроса в день**

**Максимальная нагрузка в день:**
- Обычные методы: ~1,500 запросов/день (с запасом)
- Reports.get: 24 запроса/день
- **Общий максимум: ~1,524 запросов/день (значительно ниже лимита 10,000)**

## 4. Обработка ошибок

Программа реализует многоуровневую обработку ошибок:

### 4.1. Обработка ошибок API

```python
# Классификация ошибок по типам:

1. Ошибки авторизации (коды 53, 152)
   - Действие: Логирование ошибки, прекращение работы
   - Повтор: Не выполняется, требуется обновление токена

2. Ошибки лимитов (коды 506, 509)
   - Действие: Логирование, ожидание перед повтором
   - Повтор: Экспоненциальная задержка (1 сек, 2 сек, 4 сек, ...)

3. Ошибки валидации (коды 1000, 1001)
   - Действие: Логирование, проверка параметров
   - Повтор: Не выполняется, требуется исправление кода

4. Ошибки бизнес-логики (коды 2000-2999)
   - Действие: Логирование, пропуск проблемного элемента
   - Повтор: Не выполняется для конкретного элемента

5. Ошибки сети (таймауты, соединение)
   - Действие: Логирование, повтор с задержкой
   - Повтор: До 3 раз с экспоненциальной задержкой
```

### 4.2. Механизм повторных попыток

```python
# Алгоритм повторных попыток:

1. Первая попытка: немедленно
2. Вторая попытка: через 1 секунду (если ошибка сети или rate limit)
3. Третья попытка: через 2 секунды
4. Четвертая попытка: через 4 секунды
5. После 4 неудачных попыток: прекращение, логирование ошибки
```

### 4.3. Логирование ошибок

Все ошибки логируются с указанием:
- Времени возникновения
- Метода API, который вызвал ошибку
- Кода ошибки и сообщения
- Параметров запроса
- Стектрейса (для неожиданных ошибок)

### 4.4. Примеры обработки ошибок

**Пример 1: Ошибка rate limit**
```
Ошибка: RateLimitError (код 506)
Действие: 
  - Логирование ошибки
  - Ожидание 2 секунды
  - Повтор запроса
  - Если повторная ошибка: увеличение интервала между запросами
```

**Пример 2: Ошибка авторизации**
```
Ошибка: APIRequestError (код 152)
Действие:
  - Логирование критической ошибки
  - Прекращение работы программы
  - Уведомление администратора
  - Требуется обновление токена доступа
```

**Пример 3: Ошибка сети**
```
Ошибка: requests.exceptions.Timeout
Действие:
  - Логирование ошибки
  - Повтор через 1 секунду
  - Если повторная ошибка: увеличение таймаута или пропуск запроса
```

## 5. Учет текущих ограничений API Директа

Программа полностью учитывает все ограничения Yandex Direct API:

### 5.1. Ограничения по частоте запросов

**Реализованные механизмы:**

1. **Rate Limiter класс**
   - Контроль запросов в секунду (максимум 4 запроса/сек, лимит API: 5)
   - Контроль запросов в день (максимум 9,000 запросов/день, лимит API: 10,000)
   - Контроль запросов Reports.get (максимум 90 запросов/день, лимит API: 100)
   - Автоматический сброс счетчиков в начале нового дня

2. **Межзапросная задержка**
   - Минимальный интервал между запросами: 0.25 секунды (1/4 запроса в секунду)
   - Автоматическое ожидание перед каждым запросом

3. **Мониторинг лимитов**
   - Отслеживание количества запросов в день
   - Предупреждение при приближении к лимиту (80% от максимума)
   - Прекращение работы при достижении лимита

### 5.2. Ограничения по размеру запросов

**Соблюдаемые ограничения:**

1. **Батчинг запросов**
   - Группировка запросов для уменьшения количества вызовов
   - Использование SelectionCriteria для фильтрации на стороне API

2. **Ограничение полей**
   - Запрос только необходимых полей (FieldNames)
   - Избежание запроса всех полей для экономии ресурсов

### 5.3. Ограничения по методам Reports

**Специальная обработка:**

1. **Отдельный лимит для Reports.get**
   - Собственный счетчик запросов отчетов
   - Ограничение до 90 запросов в день
   - Минимальный интервал между запросами отчетов: 1 час

2. **Оптимизация запросов отчетов**
   - Кэширование отчетов на стороне приложения
   - Запрос отчетов только за необходимый период
   - Использование DateRangeType для ограничения данных

### 5.4. Обработка ответов API

**Реализованные проверки:**

1. **Проверка структуры ответа**
   - Валидация наличия поля 'result'
   - Проверка наличия ожидаемых данных

2. **Обработка частичных ответов**
   - Обработка случаев, когда API возвращает не все данные
   - Логирование предупреждений при неполных ответах

### 5.5. Мониторинг и алертинг

**Реализованные механизмы:**

1. **Логирование всех операций**
   - Запись каждого запроса к API
   - Запись всех ошибок и предупреждений
   - Статистика использования API

2. **Метрики использования**
   - Количество запросов в день
   - Количество запросов отчетов в день
   - Средняя частота запросов
   - Количество ошибок

### 5.6. Соответствие документации API

Программа полностью соответствует официальной документации Yandex Direct API:

- ✅ Использование правильного формата запросов (JSON)
- ✅ Правильные заголовки запросов (Authorization, Client-Login)
- ✅ Корректная обработка кодов ошибок
